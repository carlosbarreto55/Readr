# repository-governance

## Purpose

Defines the repo's change-management policy: which workflow applies to which
class of work, what the authoritative durable documentation files are, and what
constitutes a trivial exception exempt from the OpenSpec workflow.

## Requirements

### Requirement: Non-trivial work MUST start as an OpenSpec change

Any work that adds, modifies, or removes functionality, behavior, data flow, or
public interface MUST begin by creating an OpenSpec change under
`openspec/changes/` before code or documentation edits begin. The change MUST
include at minimum a `proposal.md` describing what and why.

#### Scenario: Feature development requires an OpenSpec change

- **WHEN** an agent or contributor intends to implement a new feature, fix a
  non-trivial bug, refactor existing behavior, or add or remove a repository
  capability
- **THEN** the agent MUST create an OpenSpec change directory with a
  `proposal.md` BEFORE writing any implementation code or modifying canonical
  documentation files

#### Scenario: Implementation begins only after artifacts exist

- **WHEN** an OpenSpec change has been created for non-trivial work
- **THEN** implementation MUST NOT begin until the change's required artifacts
  are in `done` status per `openspec status --change "<name>" --json`

### Requirement: Trivial and read-only work MAY proceed without an OpenSpec change

The following categories are exempt from the OpenSpec workflow. This list is
exhaustive; any work not listed here is non-trivial and MUST follow the workflow.

- **Read-only exploration**: answering questions, searching the codebase,
  inspecting files
- **Direct conversation**: explaining the codebase, architecture, or design
  without making changes
- **Single-file cosmetic fixes**: whitespace, typo correction in comments or
  strings, import ordering — provided no behavioral change occurs
- **Dependency version bumps**: changing a version in `project.yml` when the API
  surface is unchanged and no code edit is required
- **Tooling configuration**: editing linter or formatter configs when no
  behavioral change results

#### Scenario: Read-only codebase exploration

- **WHEN** an agent is asked to explain, search, or analyze code without making
  changes
- **THEN** no OpenSpec change is required, and the agent MAY proceed directly

#### Scenario: Typo fix in a comment

- **WHEN** an agent corrects a single typo inside a comment or string literal
  with no behavioral change
- **THEN** no OpenSpec change is required, and the agent MAY commit directly

#### Scenario: Work outside the trivial list requires an OpenSpec change

- **WHEN** an agent intends to perform work that matches no category in the
  trivial-exemption list
- **THEN** the agent MUST create an OpenSpec change before proceeding, even if
  the change is small in scope

### Requirement: Canonical documentation files have defined ownership

Each file below SHALL be the authoritative durable truth for its scope. Content
owned by one of them MUST NOT be redefined or duplicated elsewhere.

| File | Owner scope |
| --- | --- |
| `README.md` | Project purpose, attribution, setup, quick start |
| `architecture.md` | Layer rules, contracts, invariants, architectural decisions |
| `codemap.md` | Repository structure, entry points, directory responsibilities |
| `AGENTS.md` | Agent operating rules, routing, placement, commit conventions |
| `CLAUDE.md` | Claude Code specifics only; defers to `AGENTS.md` |
| `openspec/specs/` | Normative per-capability behavior |
| `project.yml` | Xcode project structure, targets, build settings, dependencies |

#### Scenario: A layer rule changes

- **WHEN** a change alters a layer rule, contract, or invariant
- **THEN** `architecture.md` MUST be updated
- **AND** the same detail MUST NOT be restated normatively in `codemap.md`

#### Scenario: A directory is added or repurposed

- **WHEN** a change adds a directory or changes what one is responsible for
- **THEN** `codemap.md` and that directory's `codemap.md` MUST be updated

#### Scenario: Agent rules and architecture disagree

- **WHEN** `AGENTS.md` and `architecture.md` state conflicting rules
- **THEN** `architecture.md` is authoritative
- **AND** the conflict MUST be resolved rather than left to reader interpretation

### Requirement: The generated Xcode project MUST NOT be hand-edited

Project structure MUST be changed only through `project.yml`. `Readr.xcodeproj`
is generated by XcodeGen and is not tracked in version control.

#### Scenario: Project structure needs to change

- **WHEN** a target, build setting, dependency, or source path must change
- **THEN** the change MUST be made in `project.yml` and applied by running
  `xcodegen generate`
- **AND** the `.pbxproj` MUST NOT be edited directly

#### Scenario: Target structure changes

- **WHEN** a change adds or removes a target, or changes an existing target's type
- **THEN** the agent MUST obtain explicit human approval before proceeding
